# Python to CloudSim Integration Contract

Status: Stage 2A design only. This document defines the boundary; it does not implement Java, CloudSim placement, NSSAO, migration, risk calculation, or adaptive thresholding.

## 1. Python output schema

The current Python score files are:

- `outputs/azure_to_azure_scores.csv`
- `outputs/alibaba_to_alibaba_scores.csv`
- `outputs/azure_to_alibaba_scores.csv`
- `outputs/alibaba_to_azure_scores.csv`

Each row contains:

```text
dataset
entity_type
entity_id
observation_start_seconds
observation_end_seconds
member_count
start_count
mean_start_interval_seconds
mean_member_lifetime_seconds
mean_cpu_activity_percent
cpu_variability_percent_points
mean_memory_demand
cpu_resource_footprint_core_seconds
isolation_forest_score
anomaly_score
threat_score
```

The minimum Python-to-Java integration payload is:

```text
dataset,entity_type,entity_id,threat_score
```

The eight feature columns and score diagnostics may be retained for auditability, but Java/CloudSim must not use them as an implicit replacement for the threat score.

CSV encoding is UTF-8 with a header row. Fields containing commas or quotation marks must use normal CSV quoting. Numeric values use decimal notation. Missing feature values are empty CSV fields; they are not silently converted to zero. `threat_score` is required for an integration record.

## 2. Entity semantics

The entities are workload-behaviour entities, not necessarily individual users or VMs.

| Dataset | `entity_type` | `entity_id` semantics |
|---|---|---|
| `azure_v2` | `deployment` | Azure V2 `deploymentid`, representing the deployment-level workload aggregation |
| `alibaba_v2018` | `batch_job` | Alibaba V2018 `job_name`, representing the batch-job workload aggregation |

Alibaba `app_du` is excluded from the primary ML experiment because the public V2018 `container_usage` artifact has unusable blank `container_id` values, preventing a verified usage-to-application join.

`entity_id` must be treated as an opaque string. It must not be parsed, shortened, re-encoded, or assumed to be globally unique without the accompanying `dataset` and `entity_type`.

## 3. Threat-score semantics

`threat_score` is a continuous behavioural anomaly/threat indicator:

```text
0 <= threat_score <= 1
```

Higher values mean more anomalous or more threat-like workload behaviour according to the source-fitted Isolation Forest calibration. The score is not proof of malicious intent.

The current score transformation is:

```text
threat_score = clip(
    (source_raw_max - isolation_forest_score)
    / (source_raw_max - source_raw_min),
    0,
    1
)
```

The raw Isolation Forest score is retained as `isolation_forest_score`. Source-calibrated scores are suitable for within-dataset ranking. They are not directly comparable across datasets during transfer because feature distributions differ and target scores can be clipped at the source calibration bounds.

The paper's threshold `0.6` is not part of this contract and is not our adaptive threshold.

## 4. Python to Java mapping

The Java-side reader should consume the composite key:

```text
(dataset, entity_type, entity_id)
```

Required checks:

- reject empty `dataset`, `entity_type`, or `entity_id`
- reject missing or non-finite `threat_score`
- reject scores outside `[0,1]`
- reject duplicate composite keys
- preserve dataset and entity type exactly
- reject unknown dataset/entity-type combinations unless explicitly configured

Duplicate-ID behavior:

- duplicate composite keys are an input error
- no last-row-wins behavior
- no averaging or silent deduplication

Missing-value behavior:

- missing feature diagnostics may remain empty
- missing `threat_score` is an integration error
- missing metadata is an integration error

Versioning/reproducibility metadata should accompany each export:

- contract version, initially `1.0`
- dataset version
- source model name: `IsolationForest`
- feature schema version
- preprocessing configuration identifier
- random seed
- source calibration bounds
- generation timestamp

## 5. CloudSim simulation mapping

The ML entity is not automatically a CloudSim VM.

The later simulation layer must contain an explicit mapping table, for example:

```text
simulation_id,dataset,entity_type,entity_id,cloudsim_vm_id
run-001,azure_v2,deployment,<deploymentid>,vm-0001
run-001,azure_v2,deployment,<deploymentid>,vm-0002
run-001,alibaba_v2018,batch_job,<job_name>,vm-0101
```

This mapping is many-to-one from simulated VMs to a workload entity:

```text
(dataset, entity_type, entity_id) -> one or more CloudSim VM IDs
```

The mapping must be generated by the simulation configuration, not inferred from public-trace IDs. Azure deployment IDs and Alibaba job names are not CloudSim VM IDs. The mapping must be deterministic, stored with the experiment, and validated so every mapped VM has exactly one workload entity for a run.

Recommended initial implementation choice for later approval:

- create the configured number of simulated VMs for each selected workload entity
- assign the same entity threat score to each VM mapped to that entity
- retain the originating composite entity key on each simulated VM
- keep CloudSim VM IDs local to the simulation run

This is an implementation mapping, not a claim that the public traces reveal the original physical placement.

CloudSim will determine simulated VM-to-host placement. No physical co-residency is inferred from Azure or Alibaba data.

## 6. Future adaptive-threshold inputs

The future controller may consume a current state record containing:

```text
threat-score distribution statistics
current high-threat fraction
VM threat scores
server/host risk
co-residency risk
resource utilization
number of high-threat VMs
migration count
migration cost
defensive cost
computational overhead
```

These values will be produced by the simulation. No numerical values or final equation are frozen here.

Conceptual flow:

```text
current threat-score distribution
+ cloud security pressure
+ migration/defensive pressure
        |
        v
bounded adaptive threshold
        |
        v
high-anomaly / threat flag
```

The controller should be able to become stricter under higher security pressure and avoid excessive flags or migrations when defensive cost is high. Minimum, maximum, baseline, adjustment, and random-seed/configuration parameters must be explicit when the controller is implemented.

## 8. Reproducibility requirements

Each experiment must preserve:

- dataset and trace version
- source file/sample identity
- feature schema version
- preprocessing configuration
- Isolation Forest configuration
- random seed
- source calibration bounds
- contract version
- explicit entity-to-VM mapping
- CloudSim version
- Java version/configuration
- simulation configuration
- generated output directory

The current Python model configuration uses seed `20260909`, 200 estimators, `contamination=auto`, and source-size-capped `max_samples`.

## 9. CloudSim implementation surface

Verified current project:

- CloudSim version: `7.0.1`
- Maven compiler source/target: Java `21`
- Current runtime observed during audit: Java `24.0.1`
- Maven modules: `modules/cloudsim`, `modules/cloudsim-examples`

Existing examples include `CloudSimExample1` through `CloudSimExample9`, container examples, network examples, power-aware examples, and migration-related policies.

`CloudSimExample1` demonstrates the relevant lifecycle:

1. initialize CloudSim
2. create a datacenter and host list
3. create a `DatacenterBroker`
4. create `Vm` objects using the broker ID
5. submit VM lists to the broker
6. start and stop the simulation

The datacenter is created with a host list and a VM allocation policy. This is the future host/placement integration surface. The container example `ContainerInitialPlacementTest` demonstrates a separate configuration-driven placement/selection runner, but neither example is modified by Stage 2A.

## 10. Unresolved design decisions

The following remain intentionally open:

- exact CSV reader location and Java utility class
- whether each workload entity receives one or multiple simulated VMs
- simulated VM resource sizing from the feature columns
- deterministic VM-ID naming policy
- how entities with missing optional features are represented in simulation
- exact adaptive-threshold equation
- risk-model equations and weights
- host/server configuration
- co-residency representation in CloudSim
- NSSAO decision representation and objectives
- migration trigger and migration-cost model
- final security/utilization/cost trade-off

No decision in this document authorizes implementation of adaptive thresholding, placement, risk calculation, NSSAO, migration, or Java integration.
